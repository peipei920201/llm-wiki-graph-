# AGENTS.md — 預立醫療照護諮商（ACP）衛教 LLM Wiki

> 本檔是這個 wiki 的 schema。每次工作階段開始時請先完整讀過，再讀 `wiki/index.md` 與 `wiki/log.md` 最後 10 筆。
> 本檔由使用者與 Agent 共同演進；要修改規則時，先向使用者提議，經同意後再改，並在 `wiki/log.md` 記一筆 `schema`。

---

## 1. 專案目的

建立「預立醫療照護諮商（Advance Care Planning, ACP）」的衛教知識庫。

- **資料來源**：使用者提供的文獻、指引、法規、衛教資料（文字檔或 PDF）。
- **最終產出**：兩套可持續更新的衛教指南，皆由 wiki 內已入庫、可追溯的內容整理而成。
  1. **意願人篇**（`wiki/guides/patient/`）：給有意願做 ACP 的一般民眾。只講必要重點，分階段引導，避免艱澀用詞。
  2. **深入學習篇**（`wiki/guides/student/`）：給醫護、社工等相關科系學生。內容更完整，含法規與倫理脈絡、情境舉例、討論問題。
- **核心精神**：wiki 是會累積的知識庫，不是每次問答重新檢索。新資料入庫時要整合進既有頁面，並標出補強與矛盾之處。

## 2. 角色分工

| 角色 | 負責 |
|---|---|
| 使用者 | 選擇與提供資料、參與討論、決定是否入庫、最終審閱衛教內容 |
| Agent | 精讀、整理討論重點、撰寫與維護 wiki、交叉連結、記錄日誌、健檢 |

使用者幾乎不手寫 wiki；Agent 不得在未經使用者確認下入庫（見第 9 節）。

## 3. 目錄結構

```
acp-wiki/
├── AGENTS.md
├── raw/                      # 原始資料層：內容不可修改
│   ├── inbox/                # 使用者新丟入、待處理
│   ├── ingested/             # 已入庫的原檔（只搬移，不改內容）
│   ├── converted/            # PDF 轉出的 markdown（可重做）
│   └── assets/               # 圖片等附件
├── wiki/                     # Agent 維護層
│   ├── index.md              # 內容目錄（每次入庫更新）
│   ├── log.md                # 時序日誌（只增不改）
│   ├── overview.md           # 全局綜述與目前的整體論點
│   ├── glossary.md           # 術語對照表（專業詞 ↔ 白話說法 ↔ 英文）
│   ├── sources/              # 來源摘要頁（一份資料一頁）
│   ├── concepts/             # 概念頁（ACP、預立醫療決定、醫療委任代理人…）
│   ├── laws/                 # 法規與制度頁（附版本日期）
│   ├── scenarios/            # 情境案例頁（虛構、去識別）
│   ├── comparisons/          # 比較分析頁
│   ├── syntheses/            # 由問答歸檔的綜合分析
│   └── guides/
│       ├── patient/          # 意願人篇
│       └── student/          # 深入學習篇
├── tools/                    # 檢查腳本（check_slides.py）
├── exports/
│   └── slides/               # 由 wiki 頁面生成的 HTML 簡報（衍生物，可重做）
│       └── _work/<主題>/     # 簡報流程的工作檔：brief、claims、outline、slide-spec
└── templates/                # 各類頁面模板，新建頁面時複製使用
```

> 版本控制：`raw/ingested/*.pdf` 預設不納入 git（見 `.gitignore`），來源清單與取得方式記在 `raw/SOURCES.md`；入庫新來源時一併更新該清單。

## 4. 檔名規則

- **`raw/` 原檔**：`YYYY-第一作者姓或機構縮寫-關鍵詞.副檔名`，全小寫、英文與連字號，無空格。例：`2023-chen-acp-outcomes.pdf`、`2019-hpa-ad-guide.pdf`。無法確定年份時用 `nd`。
  - 轉換檔放 `raw/converted/`，檔名與原檔相同、副檔名改 `.md`。
- **`wiki/sources/`**：與原檔同名（不含副檔名），即「來源 ID」。例：`2023-chen-acp-outcomes.md`。來源 ID 是全 wiki 引用來源的唯一鍵。
- **`wiki/concepts/`、`laws/`、`comparisons/`**：使用**繁體中文名稱**為檔名，例：`預立醫療照護諮商.md`、`病人自主權利法.md`。英文原詞放 frontmatter 的 `aliases`。
- **`wiki/scenarios/`**：`scn-主題簡述.md`（中文），例：`scn-家屬意見與本人意願不同.md`。
- **`wiki/syntheses/`**：`syn-YYYYMMDD-主題.md`。
- **`wiki/guides/`**：`patient-階段編號-主題.md`、`student-單元編號-主題.md`，例：`patient-1-認識預立醫療照護諮商.md`、`student-3-法規與倫理.md`。
- **`exports/slides/`**：`patient-主題.html`、`student-主題.html`（ASCII 小寫連字號）。
- 內部連結一律用 Obsidian 格式 `[[頁面名]]`；需顯示別名時用 `[[頁面名|顯示文字]]`。

## 5. 頁面規範

所有 wiki 頁面開頭必須有 YAML frontmatter。模板在 `templates/`。

共通欄位：

```yaml
---
type: source | concept | law | scenario | comparison | synthesis | guide-patient | guide-student
title: 頁面標題
aliases: []            # 英文原詞、常見別稱
created: YYYY-MM-DD
updated: YYYY-MM-DD
status: draft | reviewed   # reviewed = 使用者已審閱確認
sources: []            # 引用的來源 ID 清單
tags: []
---
```

各類型額外欄位與必備段落以模板為準。重點：

- **source**：`jurisdiction`（適用地區）、`doc_type`（研究／指引／法規／衛教資料／其他）、`evidence_note`（研究設計與證據強度的簡述）、`raw_file`。
- **law**：`effective_version`（所依據的條文版本日期）、`verified`（是否已與官方現行條文核對：yes/no）。
- **guide-patient / guide-student**：`audience`、`stage`（或 `unit`）、`reading_level`。

## 6. 寫作與引用規範

### 6.1 語言
- 內文使用**繁體中文**（台灣用語）。
- 關鍵技術術語**保留英文原詞**：首次出現寫「中文（English）」，之後可只用中文。縮寫（ACP、AD、DNR 等）首次出現時展開。
- 術語譯名統一記在 `wiki/glossary.md`；入庫發現新術語或譯名衝突時，更新 glossary 並提醒使用者。

### 6.2 可追溯性（最重要）
- 每一個事實性主張都要標註來源：`〔來源ID，§章節或 p.頁碼〕`。例：`〔2023-chen-acp-outcomes，p.5〕`。
- 無法定位到頁碼或章節時，寫明「位置待補」，不得省略來源。
- 用標記區分三種內容性質，寫在句首或段首：
  - **【原文】**：來源明確寫出的內容（可改寫，不改原意）。
  - **【綜合】**：Agent 跨來源整合的推論，須列出所依據的來源。
  - **【待查證】**：不確定、轉換品質存疑、或來源之間矛盾。
- 數字、百分比、樣本數、條文內容，若來自 PDF 表格或圖片，需註明「經轉換，建議對照原檔」，除非已人工核對。
- 直接引用原文每次不超過兩句，加引號並標出處；其餘一律改寫。

### 6.3 地區與時效
- 每份來源都要標 `jurisdiction`。台灣以外的研究結果（例如美國的 ACP 研究）用於說明台灣做法時，必須明講「此為○○地區的資料，不等同台灣規範」。
- 法規與制度頁需註明依據的條文版本日期。**不得憑記憶寫條文內容或條號**，只能根據已入庫的來源撰寫；若來源不足，標【待查證】並請使用者提供官方文本。
- 引用的衛教資料或指引若有發布日期，保留在來源頁。

### 6.4 矛盾與不確定
- 新來源與既有頁面矛盾時：不得覆蓋舊內容。兩種說法並列，各附來源，在頁面「矛盾與爭議」段落說明差異可能原因（地區、時間、研究對象、定義），並在入庫討論時告知使用者。
- 不確定時寫「不確定」，不要補完。

## 7. 內容安全與倫理準則

本 wiki 是**衛教與教育用途**，不是個別化醫療、法律或諮商意見。

1. **不替個人做決定。** 不使用「你應該簽署／拒絕…」這類指示。可說明選項、常見考量與其影響。
2. **非指引性、尊重價值觀。** ACP 的核心是釐清當事人自己的價值觀與偏好；文字中保持中立，不暗示某種選擇較好。
3. **語氣溫和。** 避免恐嚇、悲情或輕描淡寫死亡與重症。意願人篇尤其注意。
4. **不提供個案診斷或預後判斷。**
5. **法律／醫療程序以官方與醫療機構為準。** 意願人篇每個階段結尾保留「想進一步了解或辦理，可洽詢…」的提示，具體機構與管道須有來源依據。
6. **情境案例一律虛構並去識別。** 若來源中有真實個案，只能抽象化改寫，不得保留可辨識資訊。案例頁開頭註明「虛構情境」。
7. 遇到涉及使用者自身或他人的真實個案隱私資料，提醒使用者去識別後再提供。

## 8. 兩種受眾的寫作規格

兩套指南皆為**由已入庫內容整理**的衍生頁，不得出現 concepts／laws／sources 中沒有的新主張。每段結尾以 `〔→ [[概念頁或來源頁]]〕` 指回依據。

### 8.1 意願人篇（`wiki/guides/patient/`）

- **對象**：對 ACP 有興趣或正在考慮的一般民眾與家屬。
- **閱讀程度**：國中畢業可讀懂。短句、主動語態；一段只講一個重點。
- **用詞**：
  - 專業詞優先用白話；必須使用時，首次出現加一句白話解釋。
  - 英文術語幾乎不用，必要時放括號。
  - 避免法條式語言與縮寫堆疊。
- **階段性引導**（暫定骨架，隨入庫調整，調整前先與使用者討論）：
  1. 認識：ACP 是什麼、為什麼要談
  2. 想一想：我在乎什麼、我的價值觀與偏好
  3. 聊一聊：怎麼跟家人與重要的人談
  4. 辦理：預立醫療照護諮商怎麼進行、需要準備什麼
  5. 之後：意願怎麼更新、怎麼讓醫療團隊知道
- **每個階段固定結構**：
  - 這個階段在做什麼（2～3 句）
  - 重點說明（3～5 點）
  - 想一想的問題（2～3 題）
  - 你可以先做的一件小事
  - 想進一步了解可以找誰
- 只放「必要重點」；進階細節留給深入學習篇，必要時指出「更多內容請見深入學習篇」僅供內部維護參考，不放在對民眾的文字中。

### 8.2 深入學習篇（`wiki/guides/student/`）

- **對象**：醫護、社工、諮商等相關科系學生。
- **內容較完整**：概念定位、法規與制度脈絡、倫理原則、溝通技巧、實務流程與常見困難、研究證據與限制。
- **情境舉例是必備**：每個單元至少一個情境（連到 `wiki/scenarios/`），情境後附「討論問題」與「可能的思考方向」。
- **每個單元固定結構**：
  - 學習目標
  - 核心概念（關鍵術語附英文）
  - 法規與倫理脈絡
  - 情境案例與討論
  - 常見迷思與易犯錯誤
  - 證據與限制（附來源與地區）
  - 延伸閱讀（限 wiki 內已入庫來源）
- 可使用專業術語，但首次出現要定義。

### 8.3 簡報匯出
- 簡報只能由已入庫的 wiki 頁面生成，不得加入 wiki 沒有的主張；每張投影片頁尾標註依據頁面。
- 意願人篇簡報遵守 8.1，深入學習篇簡報遵守 8.2（含虛構情境）。
- 匯出檔不修改 wiki；wiki 更新後簡報可重做。
- 簡報可放圖（流程圖、概念圖、對照圖），目的是幫助閱讀者熟悉內容。圖只能呈現主張池內已有的關係；順序或分類若為整理，圖上要註明「整理」。

## 9. 工作流程

### 9.0 總原則：先討論，後入庫
- **一次精讀一份資料**，與使用者討論重點。
- **使用者確認前，不得建立或修改 `wiki/` 內任何頁面**（日誌除外，見下）。
- 即使使用者一次丟多份資料，也逐份進行，不合併討論。

### 9.1 Intake（收件與排程）— 使用者丟入多份資料時
1. 列出 `raw/inbox/` 內所有檔案。
2. 僅做輕量掃描（標題、年份、類型、作者、長度，**不精讀**），輸出一張待處理表：

   | 序 | 檔名 | 推測類型 | 地區 | 概述（一行） | 建議順序與理由 |
   |---|---|---|---|---|---|

3. 若檔名不符合第 4 節規則，提議新檔名，經使用者同意後重新命名。
4. 請使用者確認處理順序。確認後從第一份開始進入 9.2。
5. PDF 處理：嘗試轉為文字放入 `raw/converted/`，檔頭記錄轉換工具與日期。檢查轉換品質（亂碼、表格錯位、公式、圖片遺失），在討論時回報；掃描檔需 OCR 者告知使用者品質風險。圖表重點若無法由文字取得，標【待查證】並請使用者對照原檔。

### 9.2 Discuss（精讀與討論）— 每份資料一輪
Agent 完整閱讀後，用下列結構向使用者報告（模板見 `templates/discussion-report.md`），然後**停下等待回覆**：

1. 基本資料：類型、年份、地區、研究設計／文件性質、證據強度簡述
2. 一句話摘要
3. 重點（3～7 點，各附出處位置）
4. 與現有 wiki 的關係：新增 ／ 補強 ／ 矛盾（列出對應頁面）
5. 建議入庫計畫：將新建與更新的頁面清單
6. 對兩套指南的影響：意願人篇（哪個階段、什麼必要重點）／深入學習篇（哪個單元、可延伸的情境）
7. 疑問與【待查證】事項
8. 想請使用者決定或補充的問題

使用者可回覆：調整重點、要求補充精讀某段、修改入庫計畫、或「確認入庫」／「暫不入庫」。

### 9.3 Ingest（確認後入庫）
僅在使用者明確表示可入庫後執行：

1. 在 `wiki/sources/` 建立來源頁（用模板）。
2. 新建或更新相關 `concepts/`、`laws/` 頁面，加上來源標註；處理矛盾依 6.4。
3. 新術語與譯名更新 `glossary.md`。
4. 需要情境時，新建或更新 `scenarios/` 頁面（虛構、去識別）。
5. **指南更新**：依討論中確認的計畫，更新意願人篇與深入學習篇相關頁面；若使用者沒有確認指南更新，只在回報中列為「建議後續」，不動指南。
6. 必要時更新 `overview.md`。
7. 更新 `wiki/index.md`（新頁面加入對應分類，一行摘要）。
8. 在 `wiki/log.md` 追加一筆（格式見第 10 節）。
9. 將原檔從 `raw/inbox/` 移至 `raw/ingested/`（只搬移）。
10. 回報：列出所有新建與修改的頁面，以及仍待查證的項目。新入庫頁面 `status` 先設 `draft`，使用者審閱後才改 `reviewed`。

使用者說「暫不入庫」時：原檔留在 `raw/inbox/`，於 log 記一筆 `discuss`。

### 9.4 Query（問答）
1. 先讀 `index.md`，找相關頁面，再深入閱讀。
2. 回答須附 wiki 內來源標註；wiki 沒有的內容要說明「wiki 尚無此資料」，不用自身知識補完，若有補充則明確標示為「未入庫的背景知識，需查證」。
3. 若答案有保存價值（比較、分析、整理），詢問使用者是否歸檔為 `syntheses/` 或 `comparisons/` 頁面；經同意後歸檔，並更新 index 與 log。

### 9.5 Lint（健檢）— 使用者要求時，或每累積約 10 份來源入庫後提議
檢查並回報（先回報，經同意再修）：
- 頁面之間或與來源的矛盾、過時主張
- 孤兒頁面（無入鏈）、被提及卻無頁面的概念
- 缺少來源標註的主張、缺少 `jurisdiction` 的來源
- 法規頁 `verified: no` 的清單
- `draft` 停留過久的頁面
- 指南中出現 wiki 內無依據的內容
- 意願人篇用詞是否有未解釋的專業詞、句子過長
- 深入學習篇單元是否缺情境案例
- glossary 是否缺漏或譯名不一致
- 建議可再查找的資料缺口

### 9.6 簡報流程（Slides）
以「階段＋檢查＋關卡」製作簡報，工作檔放 `exports/slides/_work/<主題>/`。意願人篇與深入學習篇共用階段 0、1，從階段 2 起分開。

| 階段 | 產出 | 檢查 | 關卡 |
|---|---|---|---|
| 0 需求定義 | brief.md | 納入頁面存在於 index；列出 draft 與待查證 | 簡短確認 |
| 1 選材 | claims.md（每條主張含錨點） | 錨點可在 wiki 找到；待查證不給意願人篇 | 無 |
| 2 大綱 | outline-patient.md、outline-student.md | 必講主張有落點、無空頁、版型主張數不超過上限、圖依據屬於本頁主張、頁數不超過上限、各篇必備頁 | A：使用者確認 |
| 3 逐頁內容 | slide-spec 檔 | 每條要點可追到主張編號；用詞與安全規則；數字對照來源 | B：使用者逐頁確認 |
| 4 簡報與收尾 | HTML | 文字與逐頁內容一致；頁尾有依據；兩版不矛盾；更新 index、log | C：使用者驗收 |

- 套版：`python3 tools/build_slides.py <主題>` 由 spec 產生 HTML，不手改 HTML 文字；要改字就改 spec 再重建。
- 腳本檢查：`python3 tools/check_slides.py <主題>`，涵蓋階段 0～4（含 HTML 與 spec 的文字一致、頁尾依據、兩版數字一致）。若環境有 Playwright，另以瀏覽器渲染檢查橫向溢出與換頁。
- 自動檢查不過：自動修正最多 2 次，仍不過就停下告知卡點。
- 關卡不同意：把意見寫入該階段檔案後重做，不跳階段。
- 發現 wiki 缺資料：停下，回到 9.2／9.3，不在簡報裡補寫；僅限來源已明載、純屬漏寫的小補正，可直接補回 draft 頁並在 log 與回報中說明。
- 來源頁更新日期晚於簡報時，標記簡報「可能過期」。
- 自我檢查不等於獨立驗證：關卡 B 需附「句子、主張編號、出處」對照供使用者抽查。

## 10. index.md 與 log.md 格式

### index.md
依類別分區：Sources／Concepts／Laws／Scenarios／Comparisons／Syntheses／Guides（意願人篇、深入學習篇）。每項格式：

```
- [[頁面名]] — 一行摘要（status；來源數或年份）
```

### log.md
只增不改，新紀錄附加在檔案末尾。每筆以固定前綴開頭，方便 `grep "^## \[" wiki/log.md | tail -5`：

```
## [YYYY-MM-DD] 動作 | 對象
- 內容摘要
- 影響頁面：[[A]]、[[B]]
```

動作類別：`intake`、`discuss`、`ingest`、`query`、`lint`、`schema`。

## 11. 禁止事項

- 不修改 `raw/` 內任何檔案內容（僅允許從 `inbox` 搬至 `ingested`、經同意後重新命名；`converted/` 可重做）。
- 未經使用者確認不得入庫、不得改動指南。
- 不憑記憶撰寫條文、數據、機構資訊；沒有來源就標【待查證】。
- 不刪除既有主張來掩蓋矛盾。
- 不在意願人篇出現 wiki 內沒有依據的內容，或給出個人化建議。
- 不在 `status: draft` 頁面上標成已審閱。

## 12. 待與使用者持續討論的事項

- 意願人篇的最終輸出形式（網頁、PDF、單張衛教海報等）
- 是否需要納入英文文獻，或以台灣資料為主
- 是否導入文獻管理工具（如 Zotero）與 citation key
- wiki 規模變大後是否加入本機搜尋工具（如 qmd）
- 意願人篇階段骨架在累積幾份資料後是否重新檢討
